# Phase 0 — Baseline-матрица runtime / live

**Дата:** 2026-03-23  
**Назначение:** зафиксировать, **что именно** относится к доказательствам из репозитория (repo-proof), а **что требует** проверки в реальной среде (runtime / live), без утверждений вида «обязательно уже в проде» без фактической верификации.

**Связанные документы:** [`PHASE0_BASELINE_TRUTH_AUDIT.md`](PHASE0_BASELINE_TRUTH_AUDIT.md), [`PHASE0_BASELINE_TRUTH_AUDIT_REPO.md`](PHASE0_BASELINE_TRUTH_AUDIT_REPO.md), [`PHASE0_EXECUTION_PLAN.md`](PHASE0_EXECUTION_PLAN.md).

---

## Легенда статусов (baseline)

| Статус | Смысл |
|--------|--------|
| **REPO** | Утверждение опирается только на файлы в репозитории и локальные команды (lint/test/build и т.п.). |
| **OPEN** | В репо заложено, но сценарий end-to-end в этой сессии **не выполнялся** — нужна явная проверка оператором. |
| **LIVE** | Требуется действие в целевой среде (URL, Supabase project, CI secrets, Stripe и т.д.); статус **не заполняется из репо** без лога/артефакта проверки. |

Ниже в колонке «Baseline» указано только то, что можно честно сказать **без** доступа к продакшену.

## Матрица

| Область | Что даёт репозиторий | Что даёт runtime / live | Baseline |
|---------|----------------------|-------------------------|----------|
| Сборка web (`npm run build`) | Скрипты, зависимости, успешный prod-build на машине с клоном | Совпадение коммита/образа с тем, что крутится на хостинге | **REPO:** build PASS на дату в baseline audit |
| Lint / Vitest | Проходят с корня монорепо | Не заменяют смоук на развёрнутом приложении | **REPO:** PASS на дату в repo-proof |
| `release:check` | Скрипт и обязательные env задокументированы | PASS в CI или у оператора с заполненным `.env` | **OPEN:** без секретов — ожидаемый FAIL (см. audit §1.7) |
| CI production | Workflow `deploy-cloudflare-prod.yml` → CF Workers; отдельно `vercel.json` | Какой контур считается каноническим для домена; зелёность job | **REPO:** оба контура описаны; **LIVE:** факт деплоя и URL |
| Миграции Supabase | 62 файла в `apps/web/supabase/migrations/` | Применённая версия на remote DB vs ожидаемая | **REPO:** наличие файлов; **LIVE:** applied state |
| Auth / сессии | Код маршрутов, middleware, Supabase-клиент | Логин и сохранение сессии на **реальном** origin | **LIVE** |
| Contact → lead | Форма, API, миграции `contact_leads` | Отправка формы → запись в админке/БД | **OPEN** (план §1 п.5) |
| Billing / Stripe | API-скелеты, webhooks в дереве, доки architecture | Подпись webhook, sandbox vs live keys | **LIVE** |
| Смоук-скрипты | `smoke:prod`, `smoke:staging`, `pilot-smoke` в workflow | Успешный прогон против живого base URL | **LIVE** |
| Мобильные приложения | Структура `ios/`, `android/` | Сборка Xcode/Gradle, установка на устройство | **REPO:** структура; **LIVE:** сборка |

## Правило формулировок

- Допустимо: «в репозитории зафиксировано …», «для подтверждения в среде нужно …».
- Недопустимо без артефакта проверки: «в проде уже …», «миграции применены», «релизный gate пройден».

Обновление матрицы: по мере появления логов CI, скринов E2E или записей в отчётах Closure — менять **только** строки, для которых есть явное доказательство, и указывать дату/источник в комментарии к коммиту или в соседнем отчёте.

## 1. Два потока работ

### Поток A — технический (платформа, качество, релиз)

Цель: сделать систему **собираемой, проверяемой, безопасной по тенантам, предсказуемой в деплое** и с честной связью «код ↔ среда».

| Область | Содержание |
|--------|------------|
| Базовая линия | Аудит репо, карта архитектуры, мастер-бэклог P0–P3 |
| Релиз и миграции | CI/CD, применение миграций Supabase, смоук как gate, откат |
| Качество | lint, тесты (Vitest), typecheck, production build |
| API и домен | согласованность `apps/web` ↔ `packages/contracts`, политики доступа |
| Наблюдаемость | логи, диагностика админ-маршрутов, видимость сбоев AI/загрузок |
| Мобильные контуры | сборка iOS/Android, соответствие контрактам worker API |

### Поток B — продуктовый (ценность для ролей и сценарии)

Цель: превратить набор модулей в **согласованный продукт** для менеджера, исполнителя и заказчика.

| Область | Содержание |
|--------|------------|
| Менеджер | единый «центр внимания», проекты, задачи, отчёты, документы, согласования |
| Исполнитель | поток отчёта/медиа/синхронизации без тупиков |
| Заказчик (owner) | модуль владельца: статус, решения, видимость без утечки менеджерских данных |
| Коммерция | контакт/лид → персистенция → видимость оператора |
| AI / Copilot | поток чата, стриминг, ограничения, документированные границы |
| Строительный интеллект | объяснимые сигналы (риски, пробелы, здоровье проекта) на реальных данных |

Потоки **не независимы**: продуктовые вехи опираются на технические gate’ы (сборка, миграции, RLS, смоук).

## 2. Вехи наивысшего приоритета: стабилизация и готовность к релизу

Ниже — **MVP release readiness** в порядке жёсткой приоритизации (сначала то, без чего нельзя честно говорить о релизе).

### Уровень R0 — блокирующий (без этого релиз недопустим)

1. **Phase 0 закрыт документально** — зафиксирована правда о репо, рисках и бэклоге (`PHASE0_*` в `docs/final/`).
2. **Production build зелёный** — подтверждено на машине CI/оператора; зафиксированы команды и результат.
3. **Стратегия миграций** — все релевантные миграции в `apps/web/supabase/migrations/` имеют ясный порядок применения и процедуру проверки (workflow `apply-migrations.yml`).
4. **Критические потоки auth / tenant / middleware** — без регрессий; изменения только узко и с тестами/смоуком.
5. **Лиды/контакт** — нет «тихой потери» заявок: путь от публичной формы до хранения и админ-обзора проверен или явно задокументирован как OPEN.

### Уровень R1 — закрытие хвостов перед расширением (Closure Sprint A)

6. **Документы: E2E для менеджера** — создание, загрузка, связь с проектом, жизненный цикл статусов, решения (approve/reject), отсутствие битых записей при ошибке загрузки.
7. **Release discipline** — постдеплой смоук (`pilot-smoke`, `smoke-prod` / `smoke-staging`) как часть дисциплины; документирован откат и env-проверки.
8. **Дрейф архитектуры** — инвентаризация и минимальная нормализация (дубли корня `lib/` vs `apps/web`, политика маршрутов, расхождения док ↔ код).

### Уровень R2 — AI-слой как продукт (Closure Sprint B)

9. **Copilot** — стриминг, fallback, отмена, бюджет контекста, семантика ошибок; валидация без «фейкового стриминга».
10. **Ограничения и честность** — явная документация того, что не RAG / не долгая память, если так.

### Уровень R3 — живая среда (Live activation)

11. **Матрица «что реально в проде»** — миграции, фичи, биллинг, cost; разделение repo-proven / runtime-proven / live-proven.
12. **Cost/budget** — только утверждения с проверкой в целевой среде или пометка OPEN.

### Уровень R4 — целостность продукта для MVP

13. **Единый менеджерский контур внимания** — здоровье, риски, документы, согласования, активность.
14. **Модуль заказчика** — роль owner, отдельные экраны/API; согласованность с `docs/product/OWNER_MODULE_MVP.md` и кодом.
15. **Мобильные приложения** — честный статус iOS vs Android; отсутствие заявлений о parity без прогона сценариев.

## 3. Сопоставление с фазами исполнения (порядок неизменен)

| Фаза | Фокус потока A (техника) | Фокус потока B (продукт) |
|------|---------------------------|---------------------------|
| 0 | Аудит, карта, бэклог, план | Границы MVP, приоритеты ценности |
| 1 | Релиз, дрейф, персистенция лидов, документы E2E | Коммерческий контур, операторская видимость |
| 2 | Транспорт AI, надёжность, тесты | Опыт Copilot в продукте |
| 3 | Миграции/среда/смоук live | Проверка менеджерских сценариев в runtime |
| 4 | Контракты API интеллекта, производительность | Объяснимый интеллект для менеджера |
| 5 | Консистентность навигации, RBAC | Control center, owner, единый workflow |
| 6 | Сборки, подписи, CI для мобильных | Пользовательские сценарии Manager/Worker |
| 7 | Наблюдаемость, runbook’и, безопасность | Поддерживаемость для операций |
| 8 | Финальная матрица модулей, E2E | Вердикт FULL/PARTIAL/OPEN по модулям |

Phase 9 — только при **FINAL PLATFORM CLOSURE = YES**.

## 4. Критерий «MVP доставлен» (сжато)

- Phase 0–1 доведены до вердикта **YES** или все OPEN явно задокументированы без преуменьшения.
- Есть разделение **repo / runtime / live** доказательств.
- Менеджер, исполнитель и заказчик имеют **сквозные сценарии без тупиков** в объёме MVP или помечены PARTIAL/OPEN в финальной матрице.
- Нет скрытых P0: каждый блокер имеет владельца, обходной путь или дату/условие снятия.

Подробный бэклог и план по неделям — `PHASE0_MASTER_BACKLOG.md` и `PHASE0_EXECUTION_PLAN.md`.
